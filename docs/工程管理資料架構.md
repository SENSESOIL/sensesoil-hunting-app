# 專案情報／工進排程：資料架構與上線路線圖

> 適用頁面：狩獵管理 →「專案情報」「工進排程」（目前只開放 admin）。
> 最後更新：2026-09-27

## 1. 現在的狀態（第 0 階段：本機試編）

| 資料 | 來源 | 能不能改 |
| --- | --- | --- |
| 專案名冊（代碼、公司、名稱） | 拾壤CRM Google Sheet「專案CRM」 | 唯讀，不動 |
| 專案欄位（階段、日期、進度、金額、近況、人員） | 示範資料，或本機試編 | 可以改，**只存在這台裝置** |
| 工項（工進排程） | 示範資料，或本機試編 | 可以改，**只存在這台裝置** |

- 編輯內容存在瀏覽器 localStorage（`ss-pm-sandbox:demo:v1`／`ss-pm-sandbox:real:v1`），以「整個專案快照」為單位，其他人看不到。
- 示範資料的修改永遠不會上傳；關閉示範不會影響任何真實資料。
- 可以用「本機試編 → 複製為試算表格式」把修改匯出成 Tab 分隔文字，直接貼到試算表。
- 清除網站資料、換手機、iOS 主畫面 App 與 Safari 分頁之間，資料都**不互通**。

## 2. 建議的正式架構

```
手機／電腦（Next.js 前端）
   │  只呼叫自己的 API，不直接碰資料庫
   ▼
Next.js API（Vercel，伺服器端）── 權限：checkPermissions（Google Apps Script 權限表）
   │  SUPABASE_SECRET_KEY（只在伺服器）
   ▼
APP 自己的 Supabase（Postgres）
   ├─ pm_projects      專案欄位（金額以「元」整數存）
   ├─ pm_work_items    工項
   ├─ pm_change_log    變更紀錄（trigger 自動寫，誰／何時／哪個欄位 from→to）
   └─ pm_mutations     冪等鍵（重送不重複套用）
   │
   └─ 每日 Cron → Google Sheet「工程資料備份」（給老闆用試算表看全貌，也是備份）
```

### 各工具分工

| 工具 | 用途 | 不做的事 |
| --- | --- | --- |
| **Supabase（APP 自己的專案）** | 唯一的真實資料：專案欄位、工項、歷程；日後的工地照片（私有 Storage） | 不讓瀏覽器直接讀寫（RLS 開、不建 policy） |
| **Google Sheets** | ① 專案名冊來源（拾壤CRM）② 一次性匯入 ③ 每日備份鏡像 | 不當即時寫入目標（沒有交易、沒有列鎖，有人排序就會寫錯列） |
| **GitHub** | 程式碼 ＋ `supabase/migrations/*.sql` | **不放資料、不放金鑰**（每次儲存變 commit、觸發重新部署、金額永遠留在歷史裡） |
| **Vercel** | 部署、環境變數、Cron | — |
| **LINE 官方帳號（Messaging API）** | 之後做每日摘要推播（LINE Notify 已於 2025-03 停止服務） | 不每次編輯都推（免費則數有限） |

### 為什麼選 Supabase

- 已經在技術棧裡（`@supabase/supabase-js` 已安裝、`hunting_tasks` 在用）。
- 真正的 Postgres：型別、check constraint、交易。手機上的輸入錯誤（完工早於開工、進度 120%、亂填類型）在資料庫層就擋下。
- 容量：200 案 × 10 工項約 2,000 列，遠低於免費方案上限。
- 注意：免費方案 7 天沒活動會暫停、沒有可下載的備份 → 用每日 Cron 備份同時保持活躍；開放給工地人員或放照片時升級 Pro（約 US$25／月）。

### 絕對不要

- **不要**把工程資料放進組織圖的 Supabase（`rynhfvyoaswynyvghyzi`）。那邊的 `org_doc` 設計成 anon 可讀，公開金鑰寫在公開頁面裡，一條錯的 policy 就會讓合約金額外流。
- **不要**用 `NEXT_PUBLIC_` 前綴放 secret key。
- **不要**照抄 `hunting_tasks` 的模式（瀏覽器用 anon key 直接讀寫）。

## 3. 上線步驟

### 第 1 階段：建表（約 15 分鐘，使用者操作）

1. 打開 Supabase Dashboard，**確認是 APP 自己的專案**（網址要等於 Vercel 的 `NEXT_PUBLIC_SUPABASE_URL`，裡面有 `hunting_tasks`）。
2. SQL Editor → 貼上 `supabase/migrations/20260927000000_pm_tables.sql` 全文 → Run（可重複執行）。
3. 用檔尾「8. 自我檢查」確認 anon 被擋、樂觀鎖與歷程正常，再清掉測試資料。
4. Project Settings → API Keys → 新增一把 secret key（`sb_secret_` 開頭）。
5. Vercel → Environment Variables（只勾 Production）：

| 變數 | 值 |
| --- | --- |
| `SUPABASE_SECRET_KEY` | 上一步的 secret key |
| `PM_STORE` | `supabase`（未設定時前端維持本機試編，先部署程式也不會壞） |
| `CRON_SECRET` | 32 bytes 以上隨機字串（第 4 階段用） |
| `SHEET_ID_PM_BACKUP` | （選用）自建的「工程資料備份」試算表 ID，共用給服務帳號為編輯者 |

> 遷移檔已在本機用 PGlite（WASM 版 Postgres）實跑驗證：可重複執行、建立／更新／刪除工項、樂觀鎖衝突、冪等重送、類型檢查、變更紀錄、anon 無法讀表或呼叫 RPC，共 14 項全部通過。

### 第 2 階段：寫入 API（約 1–2 天開發）

前端已經準備好（`useProjectOps` 的 `saveMode: "server"` 分支、`SaveRequest` 型別），尚缺伺服器端：

- `src/lib/supabase-admin.ts`：`import "server-only"`，用 `SUPABASE_SECRET_KEY` 建 client。
- `GET /api/project-ops`：`PM_STORE=supabase` 時改讀 Supabase，回傳 `writable: true`。
- `POST /api/project-ops`（前端 `useProjectOps` 已經在送，body 為 `SaveRequest`）：
  - `{ op: "saveRecord", record, expectedUpdatedAt }` → RPC `pm_save_project`（部分欄位＋樂觀鎖＋`mutationId`）
  - `{ op: "saveItems", code, items }` → RPC `pm_save_work_items`（整份清單，一個交易）
  - `{ op: "import", records, items }` → 本機試編一次上傳
  - 實作時建議把 `expectedUpdatedAt` 換成資料表的整數 `version`／`items_version`（毫秒與微秒的時間戳來回會對不上），前後端一起改。
- 上傳本機試編時，先 dry-run 逐欄顯示「伺服器目前值 → 你的值」；示範資料來的內容（尤其金額）預設不勾。
- 欄位對照：`signedAt→signed_on`、`startAt→start_on`、`dueAt→due_on`、`doneAt→done_on`、`WorkItem.start/end→start_on/end_on`、`seq→sort_order`、`kind` 同名（「施工」存 null）。

### 第 3 階段（選用）：從試算表一次匯入

老闆若習慣先在試算表整理：建「狩獵管理」試算表（分頁「專案情報」「工進排程」，表頭照 `OPS_COLUMNS`／`WORK_COLUMNS`，範本見 `狩獵管理_範本.xlsx`），匯入後把試算表封存，避免兩個真相。

### 第 4 階段：營運化

- `/api/cron/pm-backup` 每日備份到 Google Sheet ＋ 私有 bucket JSON（保留 30 天）。
- 專案頁加「歷程」分頁（讀 `pm_change_log`，可「還原這個欄位」）。

### 第 5 階段：開放給工地人員

- 移除 `ADMIN_ONLY_NAV` 的兩個頁面，改依權限表「專案情報」「工進排程」欄做欄位級權限：USER 只能看自己負責的案子、只能改工項進度／備註／照片，**看不到金額**；VIEWER（業主）只能看自己的案子。
- 離線佇列（IndexedDB outbox ＋ `mutationId` 冪等，工地地下室沒訊號也不掉資料）。
- 工地照片（Supabase Storage 私有 bucket ＋ signed URL，前端先壓到長邊 1600px）。
- LINE 每日摘要（逾期、落後、明天進場）。

## 4. 之後值得做的（依價值排序）

1. **工地照片**：進度、缺失、驗收、追加減爭議的證據。
2. **歷程與還原**：「誰把完工日延了兩週」一查就知道。
3. **基準排程**：鎖定原計畫，甘特圖畫「計畫 vs 實際」，工期展延談判有依據。
4. **施工日誌**：天氣、人力、進場工班，每天一筆。
5. **LINE 摘要**、**離線佇列**、**名冊快取表**（減少 Google Sheets API 延遲與配額）。

## 5. 風險清單

- Secret key 外流 = 整個 APP 資料庫打開。只放伺服器、可撤銷的 `sb_secret_` 金鑰，外流立刻撤銷。
- 示範資料被當真資料上傳 → 上傳前逐欄確認，示範來源的金額預設不勾。
- 本機試編只在那台裝置 → 畫面一直顯示「本機試編」，並提供匯出。
- 時區：伺服器跑 UTC，凡是算「今天」都要用 Asia/Taipei；Vercel Cron 台灣 08:00 = `0 0 * * *`。
- `next.config` 設了 `ignoreBuildErrors`：型別錯誤不會擋部署，資料庫的 check constraint 是最後防線。
- 金額單位：UI 顯示「萬」、資料存「元」整數；API 拒收小數。
