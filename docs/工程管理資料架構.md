# 專案／任務／工程照：架構與上線步驟

> 適用：狩獵管理 APP 的「專案」「任務」兩個主頁、底部「＋」上傳工程照、右上角通知鈴鐺。
> 最後更新：2026-09-28

## 1. 功能架構（重新整理後）

原本拆成「專案情報」「工進排程」兩頁，現在依使用者真正的三個需求——**專案、任務、排程**——整合成：

| 主頁 | 給誰 | 內容 |
| --- | --- | --- |
| **專案** | 管理者 | 需要注意／施工中／應收未收；專案清單（依階段分組）；點進去＝一個專案的全部：任務（清單／看板／甘特）、工程照、專案資料（日期、金額、人員、雲端資料夾） |
| **任務** | 所有人 | **我的**：今天／已排程／全部／已完成（像 Apple 提醒事項）<br>**全部**（管理者）：所有人的任務，依人、專案篩選<br>**工作量**（管理者）：每人手上幾件、逾期、未確認、接下來每天幾件 |
| **＋**（底部） | 所有人 | 拍照或選相簿 → 分批加說明 → 自動上傳到該專案 Google Drive 資料夾的「工程照」 |
| **鈴鐺**（右上） | 所有人 | 新指派、改期、完成、對方按「收到」的通知；手機推播開關 |
| **指揮中心 → 團隊** | 能進指揮中心的人 | 內部職員卡牌（穿公司制服，左右滑）、外部職員、協力廠商（自動帶入廠商CRM）、聯盟品牌 |

### 大頭照（2026-09-28 新增）

- 每個人在「指揮中心 → 團隊」上傳一張大頭照：手機上自動**找臉對齊、去背、換上公司制服**，做成統一風格的卡牌（照片只在手機處理，不送第三方；人像模型第一次使用從 Google 下載約 15MB）。
- 同一張照片會裁成圓形大頭照，全 APP 共用：任務指派改成「點大頭照選人」（下方顯示對方手上幾件）、清單上的負責人、專案參與者（疊在一起的小頭像，點開看每人手上幾件）、通知。
- 制服外型與顏色在 `src/components/team/uniform.ts` 的 `UNIFORM`，要改成公司實際制服顏色改那裡即可。
- 本人可以換自己的照片；管理者可以幫任何人換。

排程＝任務的「開始」與「期限」，在任何任務清單都能切換成 **甘特圖**；狀態切換成 **看板**（拖曳換欄＝改狀態）。

### 指派任務 → 對方一定知道（取代 LINE＋打電話）

1. 管理者新增任務、選「指派給」某人 → 對方手機跳推播、APP 鈴鐺出現紅點、任務標「新」
2. 對方打開任務 → 自動記錄「已讀」；按「收到」→ 管理者收到「已收到」通知
3. 管理者在清單上每個任務旁邊都看得到：**未讀／已讀／✓已收到**，不用再打電話確認
4. 對方回報進度、完成 → 指派的人收到通知

### 權限

| 角色 | 條件（權限表 Google Sheet） | 能做什麼 |
| --- | --- | --- |
| 管理者 | 任一欄是 **Admin**，或「專案情報／工進排程／任務追蹤」任一欄是 **Editor** | 全部：建專案、派工、看全部任務與工作量、看金額 |
| 成員 | 在權限表上、未離職 | 只看到指派給自己的任務；可改狀態、進度、備註、按收到；可以建「自己的待辦」；可以上傳工程照；看不到金額 |

要讓工地主任也能派工：在權限表把他的「任務追蹤」欄設成 Editor。

## 2. 資料放在哪裡

```
手機／電腦（前端）
   │  只呼叫 /api/pm（不直接碰資料庫）
   ▼
Next.js API（Vercel）── 身分：Google 登入 → 權限表 → 管理者／成員
   │  SUPABASE_SECRET_KEY（只在伺服器）
   ▼
APP 自己的 Supabase（Postgres）
   pm_projects      專案（名冊以拾壤CRM 為準；也可在 APP 直接新建）
   pm_tasks         任務（指派、期限、狀態、已讀、收到）
   pm_notifications 通知
   pm_push_subscriptions 手機推播訂閱
   pm_photos        工程照索引＋小縮圖（照片本身在 Google Drive）
   pm_profiles      員工的職稱、大頭照、卡牌人像（名單以權限表為準）
   pm_contacts      外部職員、協力廠商（APP 新增的）、聯盟品牌
   pm_change_log    變更紀錄（誰、何時、改了什麼）

工程照：APP → /api/pm/photos → Google Apps Script（以公司帳號執行）→ Drive「專案資料夾／工程照」
```

- **不再用 Google Sheet 存工程資料**（改在 APP 直接新建／修改）。Sheet 只剩：專案名冊（拾壤CRM）、權限表；團隊頁另外唯讀取用員工CRM 的電話、廠商CRM 的廠商名稱／工項／聯絡人／電話（身分證、生日、地址、匯款帳號一律不讀出）。
- **GitHub 只放程式與 SQL**（`supabase/migrations/`），不放資料、不放金鑰。
- **絕對不要**把工程資料放進組織圖的 Supabase（`rynhfvyoaswynyvghyzi`，那邊是公開可讀的）。
- 資料表全部開 RLS、不建 policy、撤銷 anon：瀏覽器就算拿到公開金鑰也讀不到。成員的限制在 API 與資料庫函式裡各檢查一次。

## 3. 上線步驟（約 20 分鐘，只要做一次）

### A. 資料庫（必要）

1. Supabase Dashboard → 確認是 **APP 自己的專案**（網址等於 Vercel 的 `NEXT_PUBLIC_SUPABASE_URL`，裡面有 `hunting_tasks`）
2. SQL Editor → 依序貼上並執行 `supabase/migrations/20260928000000_pm_schema.sql`、`20260929000000_pm_team.sql`（都可以重複執行）
3. Project Settings → API Keys → Secret keys → 建一把（`sb_secret_` 開頭）
4. Vercel → Settings → Environment Variables：

| 變數 | 值 | 必要 |
| --- | --- | --- |
| `SUPABASE_SECRET_KEY` | 上一步的 secret key | ✅ |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | 從本機 `.env.local` 複製 | 手機推播 |
| `VAPID_PRIVATE_KEY` | 從本機 `.env.local` 複製 | 手機推播 |
| `VAPID_SUBJECT` | `mailto:admin@sensesoil.tw`（或公司信箱） | 手機推播 |
| `PHOTO_SCRIPT_SECRET` | 從本機 `.env.local` 複製 | 工程照 |
| `PHOTO_SCRIPT_URL` | B 步驟部署後的網址 | 工程照 |

5. Redeploy。打開「任務」頁，沒有出現「還差一步」的黃色提示就成功了。

### B. 工程照上傳（Google Apps Script）

照 `apps-script/工程照上傳.gs` 檔頭的 6 個步驟部署（貼程式、填 SECRET 與上層資料夾 ID、授權、部署成網頁應用程式、把網址填進 `PHOTO_SCRIPT_URL`）。

- 找資料夾規則：專案資料裡有貼雲端資料夾連結就用它；否則在上層資料夾（含第二層）找名稱含代碼的資料夾（`A08 寶山野村`、`A08｜寶山野村` 都可以，`A080` 不會誤中）；找不到就新建。
- 專案資料夾裡找名稱含「工程照」的子資料夾（例：`04 工程照片`），沒有就新建。
- 檔名：`20260928_A08_打底_01.jpg`；Drive「說明」欄：說明、專案、工項、拍攝日、上傳者、`#工程照 #A08 #打底`（Drive 搜尋得到）。

### C. 手機推播

- Android／電腦：打開 APP → 鈴鐺或任務頁 →「開啟」。
- iPhone（iOS 16.4 以上）：Safari 分享 →「加入主畫面」→ 從主畫面圖示打開 → 再按「開啟」。
- 同一支手機換人登入會自動改綁；登出會取消這支手機的推播。

## 4. 本機開發與測試

```bash
# 假的 Supabase（PGlite），套用同一份 migration；灌測試資料
npm i --no-save @electric-sql/pglite && node scripts/pm-dev-db.mjs
# 以某人身分啟動（只在 next dev 有效）
PM_SUPABASE_URL=http://127.0.0.1:54321 SUPABASE_SECRET_KEY=dev PM_DEV_USER=someone@gmail.com PM_DEV_PHOTO_DIR=./tmp-photos npm run dev
```

- `PM_DEV_USER`：沒登入時模擬身分（權限照權限表）；`PM_DEV_PHOTO_DIR`：沒設 Apps Script 時照片存到本機資料夾。兩者正式環境都無效。
- 2026-09-28 已驗證：SQL 52＋14 項（含 v1→v2 升級、成員權限、通知、樂觀鎖、anon 被擋）、Apps Script 找資料夾 9 項、瀏覽器端到端（指派→通知→已讀→收到→回報、看板、甘特、工作量、照片上傳命名與說明、新建專案、手機版）。

## 5. 之後可以做

1. **每日摘要推播**：每天 8:00 推「今天到期／逾期」給每個人（Vercel Cron）
2. **任務留言**：任務裡來回討論，取代 LINE 對話
3. **歷程頁**：讀 `pm_change_log`，「誰把期限延了兩週」一查就知道
4. **離線佇列**：地下室沒訊號也能先記錄，有網路再送
5. **基準排程**：鎖定原計畫，甘特圖畫「計畫 vs 實際」
6. **工程照時間軸**：依工項、日期瀏覽，直接產生給業主的進度報告

## 6. 風險與注意

- `SUPABASE_SECRET_KEY` 外流＝整個 APP 資料庫打開：只放 Vercel、不可加 `NEXT_PUBLIC_`；外流就到 Supabase 撤銷換新。
- Supabase 免費方案 7 天沒活動會暫停、沒有可下載的備份；正式使用後建議升級 Pro（約 US$25／月，含每日備份）。
- 照片在 Drive、索引在 Supabase：在 Drive 手動刪照片，APP 裡的縮圖還在（點開會找不到），不影響其他功能。
- `next.config` 設了 `ignoreBuildErrors`：型別錯誤不會擋部署，資料庫的檢查（check constraint、函式裡的權限檢查）是最後防線。
